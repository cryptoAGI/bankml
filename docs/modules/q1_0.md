# `bankML/q1_0.rs` — the 1-bit Q1_0 kernel, the q8_0 activation quantizer, and f16 conversion

## Summary

`q1_0.rs` multiplies 1-bit `Q1_0` weights (ggml type 41) exactly as mainline ggml does at **b11192**, read from
that tag's source and checked against its shipped binary. A block is 18 bytes: an f16 scale `d` first, then 16
bytes of signs, least significant bit first; bit 1 is `+d`, bit 0 is `−d` (128 weights, 1.125 bits per weight).

ggml does not multiply Q1_0 by f32 activations. It first quantizes the activation to `q8_0` (32 values and an f16
scale per block), so one Q1_0 block meets four q8_0 blocks. "Bit-exact against ggml" here means against the AVX2 build
an AVX2 CPU without AVX-512 loads, the shipped `libggml-cpu-haswell.so`. On x86 every b11192 Q1_0 matmul goes
through `ggml_vec_dot_q1_0_q8_0`: repack is NEON-only and llamafile's sgemm has no Q1_0 case.

The module also holds the crate's exact f16 ↔ f32 conversions and the AVX2 `q8_0` quantizer, which `q2_0.rs`,
`f16.rs` and others reuse. The native forward pass (`forward.rs`) calls `mat_vec_par` for decode and
`mat_mul_act_par` for prompt micro-batches. `bankml gpu --verify` checks the GPU's Q1_0 kernel against these CPU bits.
Since 0.3.9 (unreleased) the q8_0 KV cache (`BANKML_CACHE_TYPE=q8_0`) stores K and V rows, and quantizes Q, with the
same `quantize_row_q8_0`, as llama.cpp's quantized cache does ([forward.md](forward.md)).

## Technical usage

Constants: `QK1_0 = 128`, `QK8_0 = 32`, `Q1_0_BYTES = 18`, `Q8_0_BYTES = 34`.

### Conversions and blocks

```rust
pub fn f16_to_f32(h: u16) -> f32                       // exact
pub fn f32_to_f16(f: f32) -> u16                       // round to nearest even, as F16C vcvtps2ph imm=0
pub fn dequantize_row(blocks: &[u8], out: &mut [f32])  // bit-exact with dequantize_row_q1_0
pub fn quantize_row_q8_0(x: &[f32], out: &mut [u8])    // ggml's AVX2 quantize_row_q8_0
```

`quantize_row_q8_0` follows the AVX2 build: `id = 127/amax`, round half to even, saturating packs (NaN becomes −128).
It is not ggml's `_ref` quantizer, which rounds half away from zero.

### Dot products

| function | what it models |
|---|---|
| `pub fn vec_dot_ref(n: usize, x: &[u8], y: &[u8]) -> f32` | scalar model of ggml's AVX2 `ggml_vec_dot_q1_0_q8_0`, float op for float op |
| `pub fn vec_dot(n: usize, x: &[u8], y: &[u8]) -> f32` | fastest path this CPU has; bits of `vec_dot_ref` |
| `pub unsafe fn vec_dot_avx2(n: usize, x: &[u8], y: &[u8]) -> f32` | the AVX2 kernel, ggml's instruction sequence |
| `pub fn vec_dot_generic(n: usize, x: &[u8], y: &[u8]) -> f32` | port of ggml's generic C, FMA-contracted as the shipped binary is; a different float order from the AVX2 result |
| `pub fn has_avx2() -> bool` | AVX2 and FMA and F16C detected at run time |

`x` is the Q1_0 row, `y` the q8_0 activation bytes, `n` a multiple of 128.

### Prepared activations

```rust
pub struct Q8Act { /* private */ }
impl Q8Act {
    pub fn from_q8_0(n: usize, q8: &[u8]) -> Self
    pub fn quantize(x: &[f32]) -> Self
    pub fn n(&self) -> usize
    pub fn qs(&self) -> &[i8]
    pub fn d(&self) -> &[f32]
}
pub fn vec_dot_act(x: &[u8], a: &Q8Act) -> f32
pub unsafe fn vec_dot_act_avx2(x: &[u8], a: &Q8Act) -> f32                        // the wrap kernel (any q)
pub unsafe fn vec_dot_act_sel_avx2(x: &[u8], a: &Q8Act) -> f32                    // the selection kernel (no q = −128)
pub unsafe fn vec_dot_act_1x4_sel_avx2(x: &[u8], cols: [&Q8Act; 4]) -> [f32; 4]  // selection, one row × four columns
```

A `Q8Act` is a q8_0 activation prepared once per token: quants contiguous, scales already f32, and per-lane sums Σq.
`vec_dot_act` has the bits of `vec_dot` on the q8_0 bytes it came from. With no `q = −128` it uses the selection
kernel (`2·Σ₊q − Σq`); if any quant is −128 it uses the wrap kernel, because ggml's i8 negation wraps there.

### Matrix products

```rust
pub fn mat_vec(w: &[u8], rows: usize, a: &Q8Act, out: &mut [f32])
pub fn mat_vec_par(pool: &crate::par::Pool, w: &[u8], rows: usize, a: &Q8Act, out: &mut [f32])
pub fn mat_mul(w: &[u8], rows: usize, n: usize, ys: &[&[u8]], out: &mut [f32])
pub fn mat_mul_par(pool: &crate::par::Pool, w: &[u8], rows: usize, n: usize, ys: &[&[u8]], out: &mut [f32])
pub fn mat_mul_act(w: &[u8], rows: usize, cols: &[Q8Act], out: &mut [f32])
pub fn mat_mul_act_par(pool: &crate::par::Pool, w: &[u8], rows: usize, cols: &[Q8Act], out: &mut [f32])
```

`mat_vec*` is decode (one column). `mat_mul*` writes `out[c·rows + r]` for a batch of columns (prefill), in 1×4 tiles
(`vec_dot_1x4_avx2`, `vec_dot_act_1x4_sel_avx2`) where the CPU has AVX2. Every element has the bits of ggml's
per-pair vec_dot. The `_par` forms run on a [`par::Pool`](par.md) and give the same bits at any thread count.

## How it is verified

- Unit tests (ordinary `cargo test`): `f16_roundtrip_all_65536`, `f16_conversions_match_f16c_hardware` (against the
  CPU's F16C on 2,000,000 random and a dense sweep of values), `dequantize_layout_scale_first_lsb_first`,
  `q8_0_matches_avx2_semantics`, `generic_matches_dequantized_math` (against f64 on dequantized data),
  `avx2_bit_exact_with_ref_randomized` (3,500 cases, including q = −128), `act_path_bit_exact_with_vec_dot`,
  `mat_vec_bit_exact_with_vec_dot`, `mat_mul_bit_exact_with_per_pair_vec_dot`, `act_tile_bit_exact`,
  `par_bit_exact_with_single_thread`.
- The ggml oracle (`#[ignore]`, `--release`): `testing/ggml_oracle.py` records what b11192's exported symbols return
  on a real model; `oracle_ggml_b11192_real_bonsai_1_7b` and `oracle_ggml_b11192_real_bonsai_8b_q1_0` re-derive every
  value through bankml's own `Mmap`. Recorded ([oracles.md](../oracles.md) §1): Bonsai-1.7B, 197 tensors,
  1,719,904,256 weights dequantized bit-exact, 788/788 q8_0 rows byte-exact, 788/788 dot products bit-exact (AVX2,
  `vec_dot_act`, and generic against ggml generic); Bonsai-8B, 254 tensors, 8,188,239,872 weights, 762/762.
- `oracle_ggml_b11192_q8_0_kv_kernels` (`forward.rs`, 0.3.9, `BANKML_GGML_LIB`): this module's `quantize_row_q8_0`
  against the shipped haswell library's, 4,000 rows byte-exact; the same test checks 4,000 q8_0 · q8_0 dot products
  bit-exact, saturating `maddubs` cases included (CHANGELOG 0.3.9).
- In-process A/B against the live library (`BANKML_GGML_LIB`): `ab_vs_ggml` and `decode_budget_q1_0` `dlopen` the
  shipped haswell library, check agreement, then time both. Benchmarks: `bench_q1_0`, `bench_q1_0_prefill`,
  `bench_q1_0_prefill_act`.

```sh
BANKML_GGML_LIB=/path/to/llama-b11192 cargo test --release -- --ignored ab_vs_ggml --nocapture --test-threads=1
```

## Advantages and efficiency

- **The binary is the reference.** A faithful port of ggml's generic C disagreed with the shipped library in the
  last bit, because GCC fused a multiply and add into an FMA. bankml reproduces the float order and FMAs of the shipped
  binary (read from the disassembly) and proves it on real tensors.
- **No multiplies on the weights.** Signs are expanded with `pshufb`, AND and compare; `(q ^ m) − m` negates where the
  weight is −1; `maddubs`/`madd` by ones do the horizontal adds. The selection kernel instead turns signs into
  {0, 1} and computes `2·Σ₊q − Σq` with Σq taken from the prepared activation.
- **Work moved out of the row loop.** In a GEMV every row reuses one activation, so `Q8Act` converts the q8 scales to
  f32 and lays out the quants once per token instead of per row and per block.
- **Prefill tiles.** One weight row against four columns shares the sign expansion across the columns. ggml b11192
  has no Q1_0 GEMM on x86; its prefill is one vec_dot per (row, column).
- **Measured** (laptop, Ryzen 3 3200U, 1 thread, [PERFORMANCE.md](../PERFORMANCE.md)): decode GEMV 12288×4096 at
  parity (1.01× min); prefill `mat_mul_act` 1.33× ggml's per-pair vec_dot median (1.27× in the gate run), and 1.135×
  the q8-byte `mat_mul` it replaced on the dev box (`bench_q1_0_prefill_act`). Whole-token 1-bit matmuls at 1–4
  threads: 0.93–1.13× of ggml (CHANGELOG 0.0.3). The AVX2 path is 15.2× the portable generic port. The 1-bit kernel
  is about 5.5× above the measured memory floor, so it is compute-bound.
- **Rejected with numbers.** 2- and 4-row register tiles for decode measured 0.95–0.99× and 0.81× of the one-row
  `mat_vec` loop's speed against ggml (2026-09-25, Ryzen 3 3200U), so the plain loop stays until a tile wins on the
  node; two further bit-exact decode variants were not faster (CHANGELOG 0.0.4).
- **Practice.** SIMD is chosen at run time (`has_avx2`), so the release build needs no `target-cpu` flag. Each AVX2
  function is `#[target_feature(enable = "avx2,fma,f16c")]` with its safety contract documented, and is reached through
  a safe wrapper that checks features and lengths. `Q8Act`'s fields are private, because the kernels read them through
  raw pointers sized by `n` (0.0.1 exposed them, which let safe code set `n` past the buffers; fixed in 0.0.2).

## Design notes

- **Source and binary.** The block layout, quantizer and kernels were read from the b11192 tag's source on
  2026-09-25. The FMA contraction of `ggml_vec_dot_q1_0_q8_0_generic` (both accumulations compiled to `vfmadd231ss`)
  was read from the shipped haswell library's disassembly the same day.
- **Versions.** The 8B oracle (`oracle_ggml_b11192_real_bonsai_8b_q1_0`) and `decode_budget_q1_0` date from 0.0.3;
  the `Q8Act` prefill path (`vec_dot_act_1x4_sel_avx2`, `mat_mul_act`, `act_tile_bit_exact`,
  `bench_q1_0_prefill_act`) from 0.0.4.
- **Why `Q8Act` stores f32 scales.** f16 → f32 is exact, so converting once per token cannot move a bit, while ggml
  converts each q8 scale per row and per block.

## Limitations

- x86_64 AVX2 is the only SIMD path. Without AVX2, FMA and F16C the scalar model runs (same bits, slower).
  NEON and AVX-512 / VNNI are open ([TODO.md](../TODO.md)).
- The oracle uses real weights with synthetic activations; bit-exactness on dumped real activations is open.
- 1-bit decode end to end is not claimed at llama-server's speed. TODO 0.4.0 lists it as open, with a re-measurement
  on a pinned, idle machine pending.
- A Q1_0 prefill GEMM beyond the current tile gain is open; porting the Q2_0 layout to Q1_0 is the named next
  experiment ([BUILD_HISTORY.md](../BUILD_HISTORY.md), P2).
